## Epic Summary

Epic 5 is complete from a story-tracking perspective: **4 of 4 stories marked done**.

The epic successfully established a coherent admin workflow:

- authenticated access to the admin surface
- flagged-pin triage and moderation actions
- admin creation of new pins
- admin editing of existing pins

The work also extended shared operational quality patterns across the codebase: reusable auth middleware, shared API test scaffolding, stronger mutation/query invalidation discipline, and more explicit server-side validation.

## What Went Well

### 1. Incremental delivery worked well

The epic built the admin experience in a clean sequence:

- secure entry first
- moderation queue second
- create flow third
- edit flow fourth

That sequence reduced risk because each story built on a stable previous layer instead of introducing many moving parts at once.

### 2. Reuse of shared patterns paid off

Several patterns clearly accelerated delivery and reduced regressions:

- `requireAdminAuth` middleware reused across admin handlers
- `vi.hoisted()` API test structure reused across server tests
- `QueryClientProvider` wrapper patterns reused across admin component tests
- shared admin dashboard shell extended instead of duplicated

This made later stories more predictable and easier to review.

### 3. Review feedback materially improved quality

The story records show multiple review passes that tightened the implementation:

- route param array guards added on shared pin endpoints
- query key correctness improved in admin queries
- pending/error/empty state coverage strengthened
- empty PATCH payload rejection added
- create/edit dashboard interaction conflicts resolved

The review loop was not just procedural; it meaningfully improved correctness.

### 4. Quality discipline stayed strong through the epic

The story records show a consistent pattern of adding tests with each story and resolving follow-up review issues before closure. That suggests the team maintained a healthy habit of finishing the feature, then hardening it.

## Challenges and Friction

### 1. Planning artifacts drifted from implementation reality

This was the clearest recurring issue.

Examples surfaced in the story notes:

- PRD scope deferred admin UI at MVP, while Epic 5 implemented a meaningful admin UI surface
- story acceptance criteria referenced fields like `source`, `fee`, and `notes` that did not exist in the actual schema
- some story language implied data model behavior that had to be corrected during implementation

This created avoidable translation work during development.

### 2. Shared-file hotspots increased coordination risk

Two files became repeated integration points:

- `api/pins/[id].ts`
- `src/features/admin/AdminDashboard.tsx`

Because these files accumulated behavior across stories, each new story had to preserve existing behavior while extending it. The code held up, but the pattern increases change risk and review burden.

### 3. Readiness checks could have happened earlier

Several fixes were discovered during review rather than before implementation began:

- schema/AC mismatches
- query key edge cases
- shared route guard cases
- empty-body validation holes
- dashboard state interaction conflicts

These are exactly the kinds of issues a stronger story-readiness pass could catch earlier.

## Key Insights

### Insight 1: Story readiness must include schema validation

When stories touch API contracts or persisted fields, the team should verify the story against the actual schema before implementation starts. This would have prevented several AC-vs-schema mismatches in Epic 5.

### Insight 2: Shared patterns are a force multiplier

The epic went faster and stayed safer where the team reused:

- auth middleware
- test harness patterns
- query invalidation conventions
- existing dashboard state structure

This is a strong argument for continuing to codify and reuse proven project patterns instead of improvising per story.

### Insight 3: Admin surfaces need explicit state contracts

The admin experience spans auth state, list state, mutation state, success messaging, and invalidation behavior. Where those contracts were explicit, implementation was smooth. Where they were implicit, review uncovered gaps.

### Insight 4: Review is especially valuable on shared endpoints

The most valuable review comments were not stylistic. They focused on endpoint safety, shared-file side effects, validation completeness, and cache behavior. Those are the right review priorities for this codebase.

## Breakthrough Moments

- Story 5.1 established the admin shell and session model, which unlocked the rest of the epic cleanly.
- Story 5.2 created the moderation backbone and introduced reliable API/test patterns reused later.
- Story 5.4 showed the benefit of extending shared endpoints carefully rather than creating parallel edit-only routes.

## Recurring Feedback Themes

- Verify requirements against the actual schema before coding.
- Be careful when extending shared files and endpoints.
- Cover error, empty, and pending states explicitly.
- Keep query keys and invalidation scopes precise.
- Prefer concrete validation over silent no-op behavior.

### Discovery 1: Scope alignment needs repair across planning artifacts

The reviewed documents do not fully agree on admin scope. The PRD defers admin UI at MVP, but the implemented roadmap includes a fully delivered admin epic. That mismatch should be corrected so future planning and prioritization are based on a single shared truth.

`api/pins/[id].ts` now handles increasingly important lifecycle operations. Future additions should consider whether the shared route remains simple enough to extend safely or whether responsibilities should be split more explicitly.
