## What Went Well

### 1. Idempotency was treated as a first-class requirement, not an afterthought

Story 5.1 layered three idempotency strategies:

1. Per-row pre-check (`trips.legacy_plan_id` lookup),
2. Database `UNIQUE(user_id, legacy_plan_id)` constraint as a race-safe guard,
3. **Stop-count integrity check** that detects partial-backfill rows and re-inserts them.

That third layer was added during code review and is the kind of detail that pays off in production migrations. It means the script can be re-run safely after any failure without leaving rows in a broken state.

### 2. Pure-function extraction kept the migration testable

`transformLegacyPlan(row) → { trip, stops } | null` was extracted from `main()`. All 12 unit tests exercise the mapping logic with no DB. This is a pattern worth re-using for any future migration script — the I/O wrapper and the transformation logic should never be the same function.

### 3. Migration story was sequenced cleanly

5.1 (data) → 5.2 (frontend cutover) → 5.3 (shared-trip import) is the right order. Each story had a small, well-defined "must NOT add" list that prevented scope creep into the next story. 5.2 explicitly deferred shared-trip import to 5.3, and 5.3 did not have to redo anything in 5.2.

### 4. Code-review found real bugs that tests had missed

Two MEDIUM issues caught in p3-5-3 review:

- `void async fn()` + `await mutateAsync` without try/catch produced unhandled promise rejection on import failure
- Raw `OFFLINE_QUEUED` error string would have been displayed to users when offline

Both were behavioral bugs that the original 12-test suite did not exercise. The adversarial review caught both before commit. This validates the create-story → dev-story → **code-review** loop as a meaningful quality gate, not just a formality.

### 5. Shared-trip import correctly leans on existing infrastructure

`PremiumGate` (auth + entitlement gating, redirect-aware) and `useCreateTripMutation` (offline queue, conflict handling) were already in place from earlier Phase 3 epics. Story 5.3's actual new code is small — a few imports and a `try/catch` around mutate. That is a sign Phase 3's foundation work (Epics 1–4) was right-sized.

## What Could Have Gone Better

### 1. `sourceTripId` linkage is structurally weak

The backfill writes `null` for `source_trip_id` (because legacy IDs are not UUIDs in the new table). Story 5.3 then uses the legacy `TripPlan.id` (a UUID happens to be present in the snapshot) as the import attribution. There is no FK enforcement and no cross-referencing — if a shared trip's source legacy plan was deleted before backfill, the imported trip carries a dangling pointer.

This is acceptable for now (attribution-only metadata), but it should be **documented as known technical debt** and revisited if any feature ever depends on resolving `source_trip_id` back to a real row.

### 2. Sprint-status drift went undetected for the entire epic

The sprint-status file had `p3-epic-5: in-progress` even after all three stories were marked `done`. The status was only corrected by the sprint-status workflow at the *end* of the epic, not progressively. We saw the same pattern at the end of Phase 2: epic statuses were updated in batches at the end of sub-epics.

**Action:** Add an explicit step to the `code-review` skill (or a post-merge hook) that flips the epic status to `done` when the last story is closed.

### 3. The 26-day staleness in `sprint-status.yaml`

`generated: 2026-03-31` was still recorded even though the file was being mutated. This is purely cosmetic, but a stale `generated` field undermines confidence in the file as a source of truth. The sprint-status workflow should rewrite the timestamp when it edits the file.

### 4. No integration test for the legacy notice

Story 5.2's "legacy plans notice" in `MyRoutesScreen` empty state is verified by mocking `useTripPlansStore`, but there is no test that exercises the *real* hydration sequence (legacy plans hydrated → normalized trips loaded → backfill catches up → notice disappears). If localStorage hydration changes, this notice could silently break and users with mid-migration state would see a broken or wrong message.

### 5. Offline error messaging path is narrow

`OFFLINE_QUEUED_ERROR === 'OFFLINE_QUEUED'` is detected by string equality at the call site. If the constant is ever renamed or the error wraps in another `Error`, the friendly message disappears and the raw string returns. A typed sentinel (or `error instanceof OfflineQueuedError`) would be more robust. Acceptable for now, but worth tightening when there's a second consumer.

## Key Insights & Lessons

1. **Migrations need three independent idempotency layers.** Pre-check + DB constraint + post-check (count integrity). The third one is what saves you from partial-failure scenarios.

2. **Defer non-essential refactors during a closing-epic.** Story 5.2 deliberately did *not* delete `RoutePlanningScreen`. Story 5.3 deliberately did *not* rebuild social features. The closing epic of a phase is the wrong time to expand scope.

3. **`void asyncFn()` pattern is a foot-gun with `await` inside.** The outer promise rejection becomes unhandled even though there's an `await`. Always wrap in try/catch when fire-and-forget is the intent.

4. **PremiumGate as a reusable boundary worked.** A single component handles three different non-premium flows (signed out, free tier, premium). It removed ~40 lines of conditional rendering from SharedTripPlanScreen.

5. **String-based error sentinels create fragile call-site coupling.** Prefer typed errors when more than one consumer needs to react to a specific failure mode.
